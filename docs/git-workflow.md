# Git 开发与发布流程

## 1. 长期分支

| 分支 | 职责 | 接收来源 |
| --- | --- | --- |
| `main` | 稳定发布分支，正式版本标签指向该分支历史中的发布提交 | `release/*`、`hotfix/*` |
| `develop` | 日常开发集成分支，汇集下一版本的功能、修复与文档 | 任务分支，以及发布和紧急修复的回合并 |

日常工作从 `develop` 创建任务分支，通过 PR 合回 `develop`。`main` 已有项目初始化提交；本次协作规范与分支初始化作为一次仓库维护提交直接进入 `develop`，后续遵循任务分支流程。

当前项目处于需求设计阶段，`main` 的现有内容是项目初始资料，尚无正式软件版本。建立分支不代表已经发布软件。

## 2. 临时分支

| 命名 | 创建起点 | 合并目标 | 示例 |
| --- | --- | --- | --- |
| `feature/<主题>` | `develop` | `develop` | `feature/session-manager` |
| `fix/<主题>` | `develop` | `develop` | `fix/serial-disconnect` |
| `docs/<主题>` | `develop` | `develop` | `docs/ble-user-flow` |
| `chore/<主题>` | `develop` | `develop` | `chore/build-config` |
| `release/<版本号>` | `develop` | `main`，随后回合并 `develop` | `release/0.1.0` |
| `hotfix/<主题>` | 对应当前发布版本的 `main` 提交 | `main`，随后回合并 `develop` | `hotfix/hid-read-crash` |

主题使用小写英文、数字和连字符。有 Issue 时可加入编号，例如 `feature/42-session-manager`。临时分支完成合并并确认变更已保留后清理。

`release/*` 是按版本创建的发布准备分支，不额外维护一个长期 `release` 分支。只有确定版本与发布范围后才创建对应分支。

## 3. 日常开发

以下以新增会话管理为例，执行前确保工作区改动已妥善保存：

```bash
git fetch origin
git switch develop
git pull --ff-only origin develop
git switch -c feature/session-manager
```

完成修改和验证后，按 [提交规范](../CONTRIBUTING.md)创建提交，将任务分支推送到远端并创建目标为 `develop` 的 PR。PR 描述应说明问题、最终行为与验证结果。

任务分支有多个整理中的提交时，可使用 Squash Merge，并将合并后的说明整理为规范的完整提交；已经拆成独立完整提交的任务，可使用 Merge Commit 保留历史。合并提交的说明使用 `chore(merge): ...` 并补充目的、合入内容及验证情况。

共享的 `main`、`develop` 及已发布标签不进行强制推送或历史改写。需要撤销已共享变更时，通过后续修复或 `revert` 提交保留记录。

## 4. 发布准备与发布

1. 从 `develop` 的明确提交创建 `release/<版本号>`，冻结该版本功能范围。
2. 在发布分支完成版本信息、更新日志、打包验证及阻塞问题修复。新功能继续进入 `develop`。
3. 按目标操作系统和已声明支持的通信能力执行验证，记录实际验证结果及已知限制。
4. 通过 PR 将发布分支合入 `main`，采用保留分支历史的 Merge Commit。
5. 在 `main` 的该次发布提交创建附注标签 `v<版本号>`，并发布与标签对应的构建产物和发布说明。构建工具确定后再补充具体打包命令。
6. 将发布分支回合并到 `develop`，保留版本信息和发布期间的修复，再清理发布分支。

`release/*`、`hotfix/*` 的双向合并使用 Merge Commit，不使用 squash 或 rebase 合并，以保留共同祖先和变更来源。

已发布版本发生紧急问题时，从当前发布对应的 `main` 提交创建 `hotfix/*`，完成修复与验证后合入 `main` 并发布补丁版本，同时将修复合回 `develop`。若有正在准备的发布分支，也要同步修复。

所有发布、远端推送和标签创建按当次任务授权执行；本文中的流程和版本示例不自动触发发布。

## 5. 版本与标签

版本遵循 [Semantic Versioning 2.0.0](https://semver.org/lang/zh-CN/)，Git 标签增加 `v` 前缀，例如 `v0.1.0`、`v0.1.0-rc.1`。

- 初期使用 `0.y.z`。本项目约定：兼容修复增加补丁号，新功能或不兼容变更增加次版本号；不兼容变更仍须在提交和发布说明中标明。
- 达到稳定兼容承诺后发布 `1.0.0`。之后兼容修复增加补丁号，兼容新功能增加次版本号，破坏兼容性的变更增加主版本号。
- 兼容性范围包括对外协议配置、保存的会话格式，以及后续公开的脚本或扩展接口。
- 预发布版本使用 `-alpha.N`、`-beta.N`、`-rc.N`，按实际发布阶段选用。
- 正式版本使用附注标签；已经发布的标签不移动、不覆盖，修正后发布新版本。
- 文档示例 `0.1.0` 不代表已决定首个发布版本，也不会仅因创建分支而生成标签。

## 6. 远端设置建议

建议为 `main` 和 `develop` 配置分支保护：限制删除和强制推送，通过 PR 集成变更。CI 建立后再将实际存在的必要检查设为合并条件。

这些是后续 GitHub 配置建议；提交本文件不会自动启用远端分支保护或状态检查。
