# CatCommStudio 产品定义

状态：v0.3 讨论草稿

日期：2026-09-22

本文区分用户已确认的方向与建议，供后续需求和交互设计使用。候选功能不代表首版承诺。

## 1. 已确认的方向

- 项目名称：CatCommStudio。
- 产品需要支持串口、蓝牙、网络、USB、HID 等通信方式。
- 通信核心库已由用户实现：[SimpleCommKit](https://github.com/graycatya/SimpleCommKit)。CatCommStudio 以复用该库为基础进行产品设计。
- 采用多进程设计：主进程主要负责创建或打开串口、网络、USB、蓝牙、HID 等通信功能子进程。
- 用户已实现脚本引擎封装 [SimpleScriptEngine](https://github.com/graycatya/SimpleScriptEngine)，并提供进程信息库 [SimpleProcessInfo](https://github.com/graycatya/SimpleProcessInfo)。现有接口边界和集成建议见[多进程架构与基础库职责](multiprocess-architecture.md)。
- 当前处于初期，需要整理需求、设计功能和 UI 交互。
- 项目已添加 Apache License 2.0 许可证。

## 2. 产品定位建议

面向嵌入式开发者、硬件工程师和测试人员的多通信调试工作台，让用户在同一应用中完成设备连接、数据收发、协议调试和问题记录。

目标用户与具体痛点仍需验证。初步假设是：用户调试不同设备时需要切换工具、重复配置指令，并且难以关联不同连接的通信记录。

建议以“连接会话”为通信操作的基本工作单位：每个会话有自己的连接配置、收发记录和发送内容；用户可以保存并重新打开。功能子进程、窗口与会话的对应关系尚未确定，同类功能是否允许多个实例、每个子进程是否容纳多个会话，以及会话间转发或同步操作，待确认。

## 3. 现有通信基础与产品范围

已核对 SimpleCommKit 的公开头文件与构建配置，版本为 `fc13bff9c71c911b18579afe95a8f71a5cbf1c32`。以下为接口能力与 UI 需求的对应关系，尚未进行构建或设备实测。详细依据见 [通信能力与产品功能映射](communication-capabilities.md)。

| 类型 | 现有核心库接口 | CatCommStudio 的产品设计重点 |
| --- | --- | --- |
| 串口 | 枚举、参数配置、读写、插拔检测 | 参数面板、连接状态、收发与日志 |
| 蓝牙 BLE | Central 角色，扫描、连接、服务/特征查询、读写、Notify/Indicate 订阅 | 设备发现、服务/特征树、按能力启用读写与订阅操作 |
| TCP / UDP | TCP 客户端/服务端；UDP 本地收发与目标地址操作 | 连接或监听配置、TCP 客户端选择、UDP 收发地址显示 |
| USB | 设备枚举、接口/端点查询、Control/Bulk/Interrupt/Isochronous 传输 | 接口与端点选择、传输类型和参数、结果展示 |
| HID | 设备枚举、多设备读写、发送 Feature Report、插拔检测 | 设备选择、Report ID 与数据长度、普通写入和 Feature Report 发送 |
| WebSocket / MQTT | WebSocket 客户端/服务端；MQTT 发布/订阅客户端 | 是否纳入首版待确认；分别需要消息面板、主题与订阅面板 |

串口、蓝牙、网络、USB、HID 均保留在产品目标中。首版优先级改为确认“哪些已有模块先接入，以及暴露哪些用户操作”。当前核对的蓝牙模块为 BLE Central；经典蓝牙 SPP/RFCOMM 和 BLE 外设角色若有需求，需单独评估。库已有能力不自动等于首版 UI 范围或各目标平台均已验证。

职责建议：主进程提供功能入口和实例管理；功能子进程管理所属会话、指令、日志、任务和数据处理，通过 SimpleCommKit 执行设备与通信操作。SimpleScriptEngine 可作为子进程内宏与脚本执行的基础；SimpleProcessInfo 可为主进程提供进程信息和监控数据。启动、关闭、进程间通信及故障恢复仍需应用层设计。各功能复用 UI 组件与交互规范，窗口归属与展现方式随 UI 方案确定。详见[架构说明](multiprocess-architecture.md)。

## 4. 候选功能分组

| 分组 | 候选功能 | 当前状态 |
| --- | --- | --- |
| 连接管理 | 新建会话、设备发现、参数配置、连接状态、保存配置 | 复用核心库通信能力，补充会话和配置管理 |
| 功能实例管理 | 创建或打开功能子进程、实例列表、进程状态与资源占用 | 多进程方向已确认；实例粒度、监控展示和生命周期细节待确认 |
| 数据收发 | 文本/HEX 输入与显示、发送回显、时间戳、收发计数、清空显示 | 建议作为基础能力 |
| 指令管理 | 发送历史、常用指令、分组、定时发送 | 结合实际使用频率确定首版范围 |
| 记录与排障 | 搜索、过滤、日志导出、错误原因与恢复操作 | 建议首版至少支持日志导出和明确错误提示 |
| 协议工具 | 帧组装、校验计算、自定义解析、脚本处理 | 待确认具体协议和使用场景 |
| 宏与自动化 | 录制操作步骤、编辑与重复执行、脚本扩展 | 已讨论使用场景并核对现有脚本封装；录制范围、异步接口及首版优先级待确认 |
| 数据分析 | 解析字段展示、实时曲线、历史回放 | 待确认；需先定义数据来源与格式 |
| 多连接协作 | 并行会话、统一时间线、数据转发 | 待确认是否属于核心场景 |

## 5. 建议优先验证的用户流程

场景假设：开发者连接一台设备，发送测试指令，查看设备返回并保存调试记录。

1. 在主进程入口选择通信功能，创建或打开对应功能子进程。
2. 功能就绪后新建或恢复会话，选择设备或填写地址，设置该通信方式所需的参数。
3. 建立连接或启动监听，明确显示当前状态。
4. 按连接类型选择操作对象，例如远端客户端、BLE 特征或 HID 报告。
5. 输入并发送测试数据，查看发送结果与接收数据。
6. 保存常用指令、连接配置和日志，供下次调试复用。
7. 结束通信并关闭会话；是否同时退出功能子进程由后续生命周期规则确定。

优先补充的异常流程：子进程启动失败、功能未就绪、进程间通信中断、子进程异常退出、找不到设备、权限不足、设备被占用、连接超时、设备拔出、远端断开、发送格式错误、持续接收时的显示与存储限制。每种情况都应说明状态、原因以及用户可以采取的下一步操作。

## 6. UI 交互原则建议

- 主进程提供统一的功能入口；不同通信功能复用会话导航、收发记录、搜索和日志的组件及交互规则，具体窗口组织方式待确认。
- 区分进程已启动、功能已就绪和设备已连接，分别显示对应状态。
- 连接配置和操作面板随通信方式变化，显示当前连接支持的功能。
- 多会话场景下，始终明确当前发送对象，避免切换后误发到其他设备。
- 区分原始收发数据与解析结果，保证用户能回看原始记录。
- 区分暂停界面滚动、暂停显示、停止接收和断开连接。
- 界面分区与导航形式在核心流程确认后，用低保真原型验证。

## 7. 首轮待确认问题

1. 平台：首版需要 Windows、Linux、macOS 中的哪些系统？
2. 优先级：五类通信中，哪些已有模块优先接入？是否首版就需要全部覆盖？WebSocket、MQTT 是否纳入？
3. 真实场景：最先用于调试哪台设备、什么协议？目前使用什么工具，最不方便的操作是什么？
4. 并行需求：是否需要同时连接多个设备，或跨通信方式转发数据？
5. 范围细节：核心库已有接口中，哪些需要提供 UI？是否还需要 BLE Central 之外的蓝牙能力、HID Feature Report 读取等额外操作？
6. 实例与窗口：按通信类型、窗口还是会话创建子进程？同类功能是否允许多个实例？功能窗口如何展示？
7. 生命周期：主进程退出时如何处理子进程？关闭会话是否退出进程？异常退出后如何恢复？
8. 自动化：是否首版提供宏录制？是否需要跨子进程流程？脚本等待、取消和运行结果如何反馈？

## 8. 下一步产出与验收方式

以多进程架构为已确认方向，结合 SimpleCommKit、SimpleScriptEngine 与 SimpleProcessInfo 的现有接口，确认目标平台、实例边界与首要场景后，形成首版需求表，逐项记录：用户任务、触发条件、操作步骤、结果、异常处理、优先级及验收条件。随后绘制主进程入口与功能界面的低保真原型，再确定 UI 技术栈、进程控制和基础库集成方式。

建议用真实设备验证第一条完整流程：主进程能够启动功能子进程并确认就绪，功能内能够建立通信、完成可核对的收发、保存记录、恢复配置，并在设备断开或子进程退出时给出明确反馈。并发进程与连接数、数据速率、日志大小和持续运行时长等指标，应根据实际场景确定数值。
